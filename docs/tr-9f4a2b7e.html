Technical Reference

Admin panel and technical details for advanced users

1. Admin Panel

Accessing the Admin Panel

Navigate to http://tidesy.local/admin (or http://<device-IP>/admin) in your browser.

Diagnostics

The admin panel header shows key device information:

  • Version/Build: Firmware version and build number (e.g., "2.9.9 UNI b0000").
  • Uptime: How long the device has been running since last restart.
  • Heap Memory: Available free memory on the ESP32.
  • WiFi Signal: Signal strength with a quality badge (Excellent/Good/Fair/Poor).
  • IP/MAC: Device network addresses.
  • LittleFS Storage: Flash filesystem usage.
  • Station file status: Whether the station directory is loaded.
  • SD Card status: Whether an SD card is inserted.

Additional diagnostic tools:

  • Load Diagnostic: Button that fetches and displays the raw /diagnostic JSON response.
  • Update Log: Button that shows the history of all firmware updates.

Settings Form

The admin settings form provides access to all the same settings as the setup wizard, plus additional options. Changes are applied immediately when you tap Save.

  • WiFi: SSID and password (change your network without factory reset).
  • Stations: Edit station IDs, clear stations, or recreate the station directory.
  • Display: Format, brightness, night hours — same as wizard.
  • Location: Interactive map picker for lat/lng.
  • Alerts: Toggle and delay slider.
  • Tide levels: Warning level and preferred range sliders.
  • Colors: 6 color pickers (not available on TidesyINK).
  • Vestaboard: Enable, IP, API key, interval, and VB tile colors.
  • Power Mode: TidesyINK only — High/Balanced/Low radio buttons.

Diagnostics Detail

The Load Diagnostic button expands a detailed view of all system parameters:

System info (version, heap, PSRAM, LittleFS, SD card), WiFi status, display/time info, and station details with current tide values.

Alert settings, tide levels, Vestaboard status, geolocation, system health check, and the Edit Settings button.

Edit Settings Form

The Edit Settings overlay provides full access to all device configuration:

WiFi, Stations (with Recreate stations.dat), Display mode and brightness sliders, System toggles, My Location with interactive map picker.

Alert toggle and delay slider, Tide Level sliders, Color pickers, Vestaboard settings (IP, API key, interval, tile colors), and Save & Restart button.

Vestaboard Views

When connected, Tidesy cycles through three views on the Vestaboard:

Detail — Tide schedule with H/L times, values, and color bar graph.

Large — Current tide, rise/fall rate, next H/L, and date.

Alerts — Active alerts with severity and event names.

Firmware Downgrade

The admin panel includes a firmware version selector that lists previous versions. Select an older version and confirm to downgrade. This downloads and installs the selected version via OTA.

SD Card Install

You can also update firmware by placing a .bin file on a microSD card:

  1. Download the firmware file from the Tidesy website.
  2. Copy the .bin file to the root of a FAT32-formatted microSD card.
  3. Insert the card into the device’s microSD slot.
  4. Restart the device — it will detect the firmware file and install it automatically.

Update Log

All firmware updates are recorded in a log stored on the device. Each entry includes the date, version number, whether it was mandatory, and the source (OTA or SD card). View the log via the admin panel’s “Update Log” button.

3. Screenshots

Overview

Tidesy can capture BMP screenshots of the display to an SD card. This is a developer/diagnostic feature available on models with display readback capability.

Supported Models

ModelMethodSupported
TidesyL / TidesyMPSRAM framebuffer readback (LovyanGFX)Yes
TidesySILI9341 SPI readback (SDO connected)Yes
TidesyINKE-paper shadow buffer captureYes
TidesyS+ILI9488 SDO not connectedNo (hardware limitation)

Enabling Screenshots

Screenshots are enabled via the admin diagnostics panel. When an SD card is detected, Take Screenshots and Stop Screenshots buttons appear. Screenshots are captured automatically at each display refresh cycle.

SCR Badge

When screenshots are active, a SCR badge (white text on dark green background) appears on the display near the countdown timer. The badge is automatically hidden during the actual screenshot capture to avoid appearing in the saved image.

The SCR badge appears to the left of other status badges. Here shown alongside the DST badge and countdown timer.

SD Card Hot-Detection

If an SD card is inserted while the device is running, opening or refreshing the diagnostics page will detect and initialize the card. The screenshot buttons will then become available.

SD Card Ejection Detection

If the SD card is removed while screenshots are active, the next screenshot write will fail. When this happens:

  • Screenshot mode is automatically disabled.
  • The ss preference is set to "0".
  • The SCR badge is removed from the display.
  • The screenshot buttons are hidden in the diagnostics panel.

To resume, insert a new SD card and re-enable screenshots from the diagnostics panel.

File Naming

Screenshots are saved as BMP files with the naming pattern: /{view}_{device}_{NNNN}.bmp

  • view: The current display view (e.g., detail, large, alert)
  • device: The board type (crow7, crow5, cyd, crep42)
  • NNNN: Monotonically increasing counter (zero-padded to 4 digits)

4. DST Handling

The Problem

NOAA tide predictions use the lst_ldt time zone (local standard/daylight time). On DST transition days, the number of 6-minute predictions changes:

  • Normal day: 240 predictions (24 hours × 10 per hour)
  • Spring forward: 230 predictions (the 2:00–2:59 AM hour doesn’t exist)
  • Fall back: 250 predictions (the 1:00–1:59 AM hour repeats)

Timestamp-Based Slot Mapping

Instead of assigning predictions by array index (which causes misalignment), Tidesy parses each prediction’s timestamp to compute the correct display slot:

slot = hour × 10 + minute / 6

This ensures predictions always map to the correct time position on the graph regardless of DST transitions.

Spring Forward (Gap Detection)

When a gap is detected (slot jumps by more than 1), the missing slots are filled with the last valid value. The graph renders these gap slots with a red line and a dimmed fill color (50% darkened version of the normal color).

Fall Back (Duplicate Detection)

When a timestamp maps to a slot at or before the previous slot, Tidesy detects a fall-back duplicate and skips those entries. A red line segment marks the transition point on the graph.

DST Badge

A DST badge (white text on red background) appears on the detail view during any day where a DST transition is detected. This badge is visible only in the detail view.

dstGapStartintFirst slot in the spring-forward gap (-1 = no gap)
dstGapEndintFirst slot after the gap

5. SD Card WiFi Setup

Overview

If the normal WiFi setup screen (AP mode) is not working for you, Tidesy supports a fallback method: place a simple text file on a micro SD card with your WiFi credentials. On first boot, the device reads the file, saves the credentials, and connects to your network automatically.

Tip: This method is useful when the AP setup screen fails to load, when configuring multiple devices with the same network, or when you prefer not to use the on-screen setup.

Step 1: Create the Setup File

Using any text editor (Notepad, TextEdit, etc.), create a file named exactly:

tidesy_setup.txt

Type your WiFi network name and password in this exact format:

SSID=YourNetworkName
Password=YourPassword
Important: The file must be named tidesy_setup.txt (all lowercase). The SSID= and Password= keys are case-sensitive. Do not add quotes around the values. Make sure there are no extra spaces before or after the = sign.

Example

For a network called “MyHomeWiFi” with password “abc123”:

SSID=MyHomeWiFi
Password=abc123

Step 2: Copy to SD Card

  1. Insert a micro SD card into your computer (using an adapter if needed).
  2. Copy tidesy_setup.txt to the root of the SD card — not inside any folder.
  3. Safely eject the SD card from your computer.

Step 3: Insert and Boot

  1. Insert the SD card into the Tidesy device’s micro SD slot.
  2. If the device has been used before, perform a Factory Reset from the admin panel (http://tidesy.local/admin) so it returns to first-boot state.
  3. Power on (or restart) the device.

During boot, the device will:

  • Detect the SD card and read tidesy_setup.txt
  • Save your WiFi credentials to the device
  • Display “SD setup completed” on screen
  • Restart and connect to your WiFi network
  • Open the Edit Settings panel so you can configure your stations

Step 4: Configure Your Stations

After the device connects to WiFi, the Edit Settings panel opens automatically on the dashboard. Use it to select your tide stations and adjust display preferences. You can also access settings later from the web dashboard at http://tidesy.local.

Placement: Keep Tidesy at least 3 feet (1 meter) from your router and other electronics. Being too close can cause connection problems.

After Setup

Once the device is configured, the SD card file is no longer needed. The device only reads tidesy_setup.txt when no WiFi credentials are stored (first boot or after a factory reset). You can remove the SD card or leave it inserted — it will not be read again until the next factory reset.

Note: If the SD card is not inserted or the file is missing, the device falls back to the normal AP setup screen. This SD method is an alternative, not a replacement.

Troubleshooting

SymptomCauseFix
Device shows AP setup screen instead of “SD setup completed” File not found on SD card Verify the file is named tidesy_setup.txt and is in the root directory (not in a subfolder)
Device shows AP setup screen despite file being present SSID or Password line is missing or malformed Check that both SSID= and Password= lines exist with values after the =
“SD setup completed” appears but device fails to connect Incorrect SSID or password in the file Double-check the network name and password; they are case-sensitive
Device boots normally and ignores the SD file WiFi credentials already stored on device Perform a Factory Reset from the admin panel first, then reboot with the SD card inserted

6. Web Firmware Updater

Overview

The Web Firmware Updater is a browser-based USB flashing tool built on ESP Web Tools. It exists as a fallback for devices on firmware versions v3.0.0 and v3.0.1, whose OTA manifest URL pointed to a Shopify CDN that cached an outdated copy of the manifest and refused to refresh. From v3.0.2 onward, devices fetch the manifest directly from GitHub Pages and self-update normally over WiFi.

Audience: end users with v3.0.0/v3.0.1 devices stuck in the cache loop. Anyone on v3.0.2 or newer should never need this.

Public URLs

ResourceURL
Updater page https://bernhardkohlmeier.github.io/tidesy-firmware-releases/updater/
Updater user guide https://bernhardkohlmeier.github.io/tidesy-firmware-releases/updater-guide.html
OTA manifest (firmware fetches this) https://bernhardkohlmeier.github.io/tidesy-firmware-releases/tidesy_manifest.json

Browser Requirements

The updater uses the Web Serial API, which is only implemented in Chromium-based desktop browsers. Supported: Google Chrome, Microsoft Edge. Not supported: Firefox, Safari, any mobile browser.

Repository Layout

All updater assets live in the tidesy-firmware-releases GitHub repository, served via GitHub Pages from the docs/ folder:

    updater-guide.html            ← User-facing guide

      firmware/
        manifest_crow5.json       ← ESP Web Tools manifest for Tidesy M
        manifest_crow7.json       ← ESP Web Tools manifest for Tidesy L

Critical: tidesy_manifest.json must live in docs/ — GitHub Pages serves only the docs/ tree. A copy at the repo root returns 404 and OTA pickup silently fails.

ESP Web Tools Manifest Format

Each board has its own manifest. Parts are listed individually with their flash offsets — do not use a single merged binary (see Pitfalls below).

{
  "name": "Tidesy M",
  "version": "3.0.2",
  "new_install_prompt_erase": true,
  "builds": [{
    "chipFamily": "ESP32-S3",
    "parts": [
      { "path": "crow5/bootloader.bin", "offset": 0 },
      { "path": "crow5/partitions.bin", "offset": 32768 },
      { "path": "crow5/boot_app0.bin",  "offset": 57344 },
      { "path": "crow5/firmware.bin",   "offset": 65536 }
    ]
  }]
}

Key fields:

  • name — shown to the user in the install dialog. Uses the device branding (Tidesy M, Tidesy L), not the internal board codename.
  • new_install_prompt_erase: true — presents the user with an “Erase device” checkbox. Leaving it unchecked preserves NVS (WiFi credentials, station selection, brightness, all prefs entries).
  • parts — one entry per flash region. ESP Web Tools writes only these byte ranges, leaving the NVS partition at 0x9000 completely untouched.

Partition Layout (ESP32-S3, custom partitions.csv)

NameOffsetSizeNotes
bootloader0x0000~20 KBWritten by updater
partition table0x80003 KBWritten by updater
nvs0x900020 KBHolds all prefs — updater MUST NOT touch
otadata (boot_app0)0xe0008 KBWritten by updater
app0 (ota_0)0x100001856 KBWritten by updater (firmware.bin)
app1 (ota_1)0x1E00001856 KBUntouched
spiffs (LittleFS)0x3B0000320 KBUntouched (firmware auto-formats if blank)

Building the Binaries

For each board, compile with the standard Arduino CLI command and copy four artifacts from the build directory:

  1. Tidesy.ino.bootloader.bin → firmware/<board>/bootloader.bin
  2. Tidesy.ino.partitions.bin → firmware/<board>/partitions.bin
  3. boot_app0.bin from the ESP32 core (AppData/Local/Arduino15/packages/esp32/hardware/esp32/3.1.1/tools/partitions/boot_app0.bin) → firmware/<board>/boot_app0.bin
  4. Tidesy.ino.bin → firmware/<board>/firmware.bin

Firmware-Side Safety Net

To make the updater robust against edge cases, the firmware itself includes two critical safeguards:

  • LittleFS.begin(true) in setup() — auto-formats a blank or corrupt LittleFS partition on first boot. Without this, a device whose LittleFS was wiped (e.g. user picked “Erase device”) would brick at “Loading config…” because LittleFS.begin() returned false and setup() early-returned.
  • UPGRADE_PATH in Tidesy.ino — points to the GitHub Pages manifest URL, not the legacy Shopify CDN URL. From v3.0.2 onward, devices fetch https://bernhardkohlmeier.github.io/tidesy-firmware-releases/tidesy_manifest.json directly.

Pitfalls (lessons learned)

SymptomCauseFix
Device bricks at “Loading config…” after web update Merged binary did not include LittleFS image; LittleFS.begin() returned false on a partition the new partition table created blank Add LittleFS.begin(true) for auto-format on failure
Web update wipes all user prefs (WiFi creds, stations, etc.) Single merged binary. esptool merge-bin produces a contiguous image from 0x0 to the highest written offset, with the gaps (including NVS at 0x9000–0xe000) padded with 0xFF. ESP Web Tools then erases and writes 0xFF over NVS sectors, wiping prefs every install. Never use a merged binary. List each part individually in the manifest with its actual flash offset. Esptool erases only the sectors covering each part.
Web update wipes prefs even with “Don’t erase” selected Same merged-binary bug above. new_install_prompt_erase: true alone is not enough. Multi-part manifest is the actual fix; the prompt is just user-friendliness.
Devices never pick up new OTA versions from the manifest tidesy_manifest.json at the repo root returns 404 from GitHub Pages Move it to docs/tidesy_manifest.json

Adding a New Board

  1. Compile the firmware for the target board with the standard Arduino CLI command.
  2. Create docs/updater/firmware/<board>/ and copy the four artifacts (bootloader.bin, partitions.bin, boot_app0.bin, firmware.bin).
  3. Create docs/updater/firmware/manifest_<board>.json using the template above. Set name to the user-facing branding (e.g. Tidesy XL) and chipFamily to match the target chip.
  4. Add a new <option> entry to the dropdown in docs/updater/index.html and a matching key in the manifests object in the page’s script block.
  5. Push to tidesy-firmware-releases; GitHub Pages picks it up automatically.

7. Production Script (produce.py)

Purpose

produce.py turns a blank ESP32 board into a shipping-ready Tidesy device in one command. It handles the full sequence: erase flash, build and upload LittleFS, compile firmware with the correct board define, upload firmware, verify the chip, and optionally register the board’s MAC address with Tidesy Cloud inventory.

Audience: production/assembly operator. Not used for normal development flashes — use arduino-cli directly for dev work.

Usage

py -3 produce.py                    # fully interactive
py -3 produce.py CROW7              # skip board prompt
py -3 produce.py CROW7 COM5         # skip board + port detection
echo "n" | py -3 produce.py CROW7 COM5   # skip demo + registration prompts

Interactive Prompts

  1. Board — skipped if passed as first argument. CROW7 is the default.
  2. Demo build? [y/N] — yes prompts for a customer name; the name is compiled into the firmware via a -DDEMO_BUILD="..." flag and propagated to the cloud registration.
  3. Register with Tidesy Cloud? [y/N] — default No. See “Cloud Registration” below.

Production Sequence

StepActionTool
1Erase flashesptool erase_flash
2Build + upload LittleFS (stations.dat, help.html, logo)mklittlefs + esptool
3Compile firmware with -D<BOARD> define and board-specific FQBNarduino-cli compile
4Upload firmware (using the same FQBN so partition table matches)arduino-cli upload
5Verify: read chip ID, dump boot log for ~10 sesptool chip_id + arduino-cli monitor

Any step failure aborts the script immediately. The board is considered unshippable on failure and must be re-run from step 1.

Auto-Detection

The script auto-detects platform and tool paths on each run:

  • arduino-cli — checks C:\Program Files\Arduino CLI, F:\Program Files\Arduino CLI, Arduino IDE bundled, Homebrew on Apple Silicon, and $PATH.
  • esptool — prefers python3 -m esptool on Mac (for Apple Silicon), Arduino15 binary on Windows, $PATH fallback elsewhere.
  • libraries path — Windows: c:/Users/bernh/OneDrive/Arduino/libraries. macOS: OneDrive then ~/Documents/Arduino/libraries.
  • Serial port — arduino-cli board list picks the first matching ESP32 device.

Cloud Registration

When the operator answers y to the registration prompt, after a clean flash the script runs esptool read_mac, parses the MAC address, and POSTs a record to https://app.tidesy.com/api/admin/produce.

Authentication

The endpoint is gated by a shared secret in the X-Produce-Secret header, compared in constant time against the server’s TIDESY_PRODUCE_SECRET environment variable. The script reads the same value from its own environment. If the variable is unset, the call is skipped with a warning — production firmware is already flashed, so a missing secret never aborts a run.

PlatformCommand
Windowssetx TIDESY_PRODUCE_SECRET "...secret..." (new shell required)
macOS (zsh)echo 'export TIDESY_PRODUCE_SECRET="...secret..."' >> ~/.zshrc
VercelProject Settings → Environment Variables → Production

All four environments (Seattle, Beach, Laptop, Beach Mac) plus Vercel must share the same value.

Payload

{
  "mac_address": "aa:bb:cc:dd:ee:ff",
  "board_type": "CROW7",
  "firmware_version": "3.1.0 UNI",
  "firmware_build": 57,
  "demo_customer": null,
  "produced_by": "<hostname>"
}

Idempotency

The server upserts by mac_address. Re-flashing an already-produced board returns { already_existed: true } and the script prints a note with the original production date — it does not overwrite produced_at, so the inventory history is preserved.

Back-fill

Devices that shipped before the cloud registration feature existed are back-filled automatically. When any device calls POST /api/sync with a MAC that has no produced_devices row, the cloud creates a sparse inventory record (firmware version and build from prefs; produced_at, board_type, produced_by, and demo_customer left blank). The operator fills in the missing fields manually at /admin/produced/<mac>.

Output Artifacts

After a successful run, produce.py does not write binaries anywhere the user needs to touch — binaries end up in the per-board arduino-cli build directory. For archival release binaries, use release.py instead.

8. Release Script (release.py)

Purpose

release.py compiles production-quality firmware for every board, publishes the binaries as assets on a GitHub Release, updates the OTA manifest with the new download URLs, stamps user-facing docs with the version and release date, and publishes the updated docs to GitHub Pages. It ends with a manual step to upload the refreshed manifest to Shopify.

Audience: project maintainer cutting a new firmware version. Not run on assembly machines.

Usage

py -3 release.py          # fully interactive

Pre-flight Checklist

  1. Bump VERSION_STR and VERSION_INT in Version.h (script aborts if the version string is missing from the file).
  2. Reset BUILD_NUMBER to 0 on a version bump.
  3. Create .release.env next to release.py with a GitHub personal access token: 
    GITHUB_TOKEN=ghp_xxxxxxxxxxxxxxxxxxxx
    or export GITHUB_TOKEN in the shell. The token needs the public_repo scope (or repo for private).
  4. Make sure requests is installed: py -3 -m pip install requests

Interactive Prompts

  1. Version — defaults to the value currently in Version.h.
  2. Release date — defaults to today.
  3. Boards — multi-select, defaults to all three user-facing boards (CROW7, CROW5, CYD).
  4. Release notes — multi-line input; used for both the GitHub Release body and the manifest’s releaseNotes field.
  5. Mandatory update? — yes marks the manifest’s mandatory flag so devices OTA-update on next midnight check.
  6. Add in-app release message? — yes writes a dated message into manifest.messages[], shown in the device admin panel.
  7. Dry run? — yes compiles and stops before any GitHub operations, useful for verifying the build produces valid binaries.

Release Sequence

StepAction
0Stamp manual.html, tr-9f4a2b7e.html, and the updater guide with the new version and release date.
1Compile each selected board with DEBUG_LEVEL=0, screenshot disabled, and the matching -D<BOARD> define. Output .bin files land in release/ with the naming scheme tidesy_v<VERSION_INT>_<prefix>_<date>.bin.
2Create the GitHub Release (tag v<version>) and upload each firmware binary as an asset. If the tag already exists, the script asks for confirmation to delete and recreate.
3Rewrite tidesy_manifest.json with the new release’s GitHub download URLs, version, release date, mandatory flag, and notes. Optionally append an entry to messages[].
4Verify every firmware URL in the manifest is downloadable (HEAD request to each asset).
5Bump the cache-busting timestamp in UPGRADE_PATH in Tidesy.ino so shipped devices fetch the new manifest on their next check.
6Publish the updated docs (docs/manual/, docs/updater/, tidesy_manifest.json) to GitHub Pages in the tidesy-firmware-releases repository.
7Open the Shopify Files admin in a browser and prompt for a manual upload of the new manifest (legacy path for v3.0.0/v3.0.1 devices).

Build Flags & Artifacts

Release builds differ from developer builds in two ways:

  • DEBUG_LEVEL is temporarily patched to 0 in Version.h during compile, then restored.
  • SCREENSHOT_CAPABLE is forced off so shipped firmware does not write SD captures.

Built binaries are copied both to release/ (flat) and to build/<BOARD>/ (per-board archive) for the commit.

Dry Run

Always dry-run before a real release. A dry run runs steps 0–1 only: docs stamping and the per-board compile. It prints the output filename and size, then stops before any GitHub operation. Use this to verify the version string, flags, and doc stamps before committing to a tag.

Recovery

SymptomFix
GitHub release already existsScript prompts to delete and recreate. Safe — the tag is re-pushed.
Manifest URL verification failsGitHub asset upload probably timed out. Re-run with the “delete and recreate” prompt answered yes.
GitHub Pages not updatedCheck tidesy-firmware-releases repo on the web; Pages can lag 30–60 s after push.
Shopify manifest out of dateOnly affects v3.0.0 / v3.0.1 devices. Upload manually via Shopify admin (URL printed at the end of the run).

After a Release

  1. Recompile the dev CROW7 build with your usual settings so the dev device is back to DEBUG_LEVEL ≠ 0.
  2. git add Tidesy.ino release/ build/
  3. git commit -m "Release v<version>"
  4. git push
